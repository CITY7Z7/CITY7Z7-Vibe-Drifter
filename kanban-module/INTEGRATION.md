# Руководство по интеграции модуля «Kanban-оркестратор задач» (INTEGRATION.md)

Это руководство предназначено для **ИИ-агента или инженера**, выполняющего перенос данного модуля в сторонний проект (новостной автоматизатор, CMS, микросервис, админ-панель и т.д.).

---

## 1. ФИЛОСОФИЯ ПЕРЕНОСА: ИНЪЕКЦИЯ, А НЕ ЧЁРНЫЙ ЯЩИК

Модуль спроектирован **не как внешний npm-пакет**, а как **рабочая эталонная реализация и спецификация поведения**.

Когда папка `kanban-module/` копируется в проект хозяина, агент хозяина читает код модуля и:
1. **Инъекция (рекомендуется по умолчанию):** Переносит и адаптирует логику ядра прямо в стек, архитектурные слои и соглашения об именовании приложения-хозяина. Тесты модуля (`tests/`) служат формальной спецификацией того, что инварианты поведения не нарушены.
2. **Прямое подключение (как есть):** Используется, если стек хозяина совпадает (TypeScript, React, Express, SQLite) и требуется минимальное вмешательство.

---

## 2. ПОШАГОВЫЙ АЛГОРИТМ ПЕРЕНОСА

### Шаг 1. Анализ проекта-хозяина
1. Прочтите `AGENTS.md`, `README.md`, `package.json` и структуру каталогов хозяина.
2. Определите стек:
   - Backend: Express, Fastify, NestJS, Next.js API, Django, Go, Spring?
   - База данных: PostgreSQL (Prisma, Drizzle, TypeORM), SQLite, MySQL, MongoDB?
   - Frontend: React, Vue, Svelte, Solid, чистый HTML/JS?
   - Стейт-менеджер: Zustand, Redux Toolkit, Pinia, React Context?
   - UI-библиотека: Tailwind CSS, CSS Modules, Shadcn/UI, MUI?
3. **Проверка на существующую доску:** Проверьте, нет ли уже в проекте сущностей `Task`, `Board`, Kanban-интерфейсов.
   - *Если уже есть:* НЕ создавайте дубликат. Предложите пользователю расширить существующие модели полями `depends_on`, `priority`, `executor`, `attempts` и внедрить шедулер оркестрации.

### Шаг 2. Изучение ядра и тестов модуля
Прочитайте эталонные файлы:
- `kanban-module/src/core/types.ts` — доменная модель;
- `kanban-module/src/core/graph.ts` — проверка DAG, валидация отсутствия циклов, расчет слоев визуализации;
- `kanban-module/src/core/scheduler.ts` — шедулер, параллелизм (`maxParallel`), каскад ошибок (`blocked`), авто-цепочки (`autoChain`);
- `kanban-module/src/core/planner-parser.ts` — парсер планов;
- `kanban-module/tests/` — тесты (15 эталонных тест-кейсов).

### Шаг 3. Перенос хранилища (База данных)
1. **Имена таблиц:**
   - Если сохраняется SQLite/реляционная БД: используйте префикс `kanban_*` (`kanban_boards`, `kanban_tasks`, `kanban_templates`, `kanban_chat_messages`) во избежание коллизий.
   - Если у хозяина принята ORM (Prisma / Drizzle): добавьте схему в существующий файл схемы хозяина.
2. **Миграции:**
   - Делайте миграции строго идемпотентными (`IF NOT EXISTS`).
   - Поля массивов (`depends_on`, `labels`, `log`, `meta`) сериализуйте в JSON или нативные массивы СУБД (PostgreSQL `text[]` / `jsonb`).

### Шаг 4. Серверный слой и роутинг
1. **Никаких отдельных портов!** Модуль монтируется в существующий HTTP-сервер хозяина.
2. Вызовите фабрику или перенесите обработчики:
   ```ts
   // Пример монтирования в существующий Express-сервер:
   import { createKanban } from './modules/kanban';
   
   const kanban = createKanban({
     storage: new PostgresStorageAdapter(pool),
     executors: [myAppExecutor],
     routerOptions: { auth: myAuthMiddleware }
   });
   
   await kanban.init();
   app.use('/api/kanban', kanban.router);
   ```
3. Подключите middleware авторизации хозяина в `routerOptions.auth`.

### Шаг 5. UI и клиентский слой
1. Встройте компонент `<KanbanBoard apiBase="/api/kanban" />` в нужное место (вкладка админки, боковая панель, отдельный маршрут роутера хозяина).
2. **Изоляция стилей:** Модуль использует изолированные классы `kb-*` и локальные CSS-переменные для тем оформления. Он не трогает глобальные стили (`body`, `html`, `*`).
3. Если фронтенд хозяина не на React (например, Vue или Svelte) — перепишите логику хука `useKanban` на Composition API / Stores хозяина.

### Шаг 6. Исполнители (TaskExecutors) — Ключевой шаг!
Главная ценность оркестратора — запуск реальных действий хозяина:
1. Составьте список автоматизируемых действий хост-системы (например: «Сбор новостей из RSS», «Генерация саммари через LLM», «Публикация в Telegram», «Экспорт в базу данных»).
2. Реализуйте интерфейс `TaskExecutor`:
   ```ts
   export class TelegramPublisherExecutor implements TaskExecutor {
     readonly id = 'telegram_publisher';
     async run(task: Task, ctx: ExecutionContext): Promise<ExecutionResult> {
       ctx.log('Подготовка сообщения к отправке в канал...');
       // Извлекаем результат предыдущей задачи из ctx.deps:
       const text = ctx.deps['previous-task-id']?.output?.summary;
       await bot.sendMessage(channelId, text);
       ctx.progress(100);
       return { ok: true, output: { messageId: 123 } };
     }
   }
   ```
3. Зарегистрируйте исполнителей в `executors`.

### Шаг 7. Шаблоны задач под домен хозяина
1. Добавьте в БД или конфигурацию готовые промпт-шаблоны под сценарии хозяина (например, «Сбор, рерайт и публикация дайджеста»).

### Шаг 8. Валидация и смоук-тестирование
1. Запустите тесты: `npm test`. Убедитесь, что все 15 тест-кейсов зеленые.
2. Проведите сквозной сценарий: создайте цепочку `1 → 2 → 3`, запустите задачу 1, проверьте последовательное выполнение, логи и переход в `Done`.

## 3. СОГЛАШЕНИЯ ОБ ИЗОЛЯЦИИ ЭТАЛОНА

| Элемент | Префикс эталона | Правило переноса |
|---|---|---|
| Таблицы БД | `kanban_*` | Сохранить или согласовать с ORM хозяина без конфликтов |
| API маршруты | `/api/kanban/*` | Настраивается через `apiBase` |
| Переменные окружения | `KANBAN_*` | Читать через единый конфиг хозяина |
| CSS-классы | `kb-*` | Не использовать глобальный reset, скоупить стили |
| LocalStorage | `kanban:*` | Только префиксированные ключи UI |
