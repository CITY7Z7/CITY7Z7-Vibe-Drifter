## 🏛️ Главные заповеди инженера (Core Principles)

### 1. Документированность кода на 100% (High-Documentation Discipline)
- **Каждый файл:** Обязан начинаться с JSDoc/TSDoc блока `@file` и `@description`, раскрывающего назначение, архитектурный слой и ключевые зависимости файла.
- **Каждая функция, метод и класс:** Должны сопровождаться полным JSDoc/TSDoc описанием: что делает функция, описание параметров `@param`, возвращаемое значение `@returns`, выбрасываемые исключения `@throws` и возможные сайд-эффекты.
- **Обильные содержательные комментарии внутри функций:** Никаких «черных ящиков». Каждый неочевидный шаг, математический расчет, логическое ветвление, асинхронный каскад, обработка краевых случаев или транзакционный барьер должны быть снабжены развернутыми комментариями на русском или английском языке, объясняющими **«почему именно так»** и **«как это устроено под капотом»**.
- **Типизация:** Запрещен тип `any` без исчерпывающего обоснования в комментарии. Используйте строгие `interface`, `type`, `readonly` свойства и дискриминантные объединения (`discriminated unions`).

### 2. Чистота, лаконичность и производительность (Clean & Performant Code)
- Применяйте принципы **SOLID**, **KISS** и **DRY**. Не создавайте избыточных абстракций, пока в них нет реальной потребности.
- Алгоритмическая эффективность: знайте асимптотику алгоритмов (O(V+E) для обхода графа зависимостей, O(1) для поиска в хеш-таблицах и индексах).
- Ресурсосбережение: управляйте жизненным циклом таймеров, слушателей событий, SSE-подключений и соединений с базой данных. Всегда реализуйте очистку ресурсов (`cleanup`, `abortController`, `removeEventListener`).

### 3. Исчерпывающее объяснение механики (Self-Explaining Engineering)
- Перед внесением сложных архитектурных изменений или реализацией нового слоя всегда кратко, но исчерпывающе сформулируйте ментальную модель задачи.
- При ответе пользователю объясняйте суть работы системы: схемы переходов состояний (FSM), топологическую сортировку графов, реактивные шины данных, межпроцессное взаимодействие.

### 4. Документация — эталон высоких знаний (Living Single Source of Truth)
- Документация в папке `/docs/` и корневом `README.md` должна быть **актуальной, точной и всеобъемлющей**.
- **Кольцевая связанность (Ring Navigation):** Вся документация связана в неразрывное кольцо взаимных ссылок. Ни один документ не должен быть тупиком. Инженер или ИИ-агент, читая любой файл, должен иметь возможность перейти к смежным архитектурным узлам, API, руководству по стилю и журналу изменений.
- Запрещены поверхностные «рыбы» (Lorem Ipsum, TODO, "будет добавлено позже"). Если модуль существует — он описан досконально.

## 📐 Архитектурные стандарты проекта «CITY7Z7-Vibe-Drifter»

### 1. Архитектура слоев (Layered Isolation)
```
┌────────────────────────────────────────────────────────┐
│                   UI Layer (React 19)                  │
│       KanbanBoard, Column, TaskCard, DependencyGraph   │
├────────────────────────────────────────────────────────┤
│             Reactive Transport (SSE / REST)            │
│               createKanbanRouter, SSEManager           │
├────────────────────────────────────────────────────────┤
│                 Core Orchestration Layer               │
│         Scheduler, Graph (DAG), Planner, Events        │
├───────────────────┬────────────────────────────────────┤
│ Pluggable Storage │       Pluggable TaskExecutors      │
│  SQLite / Memory  │        Mock / HTTP / Shell         │
└───────────────────┴────────────────────────────────────┘
```

1. **Core (`kanban-module/src/core/`):** Чистый TypeScript. Никаких внешних библиотек, зависимости от Node.js или React. Только строгая логика графов, очередей, топологии и конечного автомата состояний.
2. **Storage (`kanban-module/src/storage/`):** Абстракция через контракт `StorageAdapter`. Любое хранилище должно быть идемпотентным, потокобезопасным и снабженным транзакционными гарантиями.
3. **Executors (`kanban-module/src/executors/`):** Контракт `TaskExecutor`. Поддержка передачи входных данных из зависимостей через `ctx.deps`, логирования в реальном времени через `ctx.log` и сигналов прерывания через `ctx.signal` (AbortSignal).
4. **Server (`kanban-module/src/server/`):** Express Router, создаваемый фабрикой `createKanbanRouter`. Не занимает свой порт! Монтируется в родительский веб-сервер. Валидация входных данных через Zod.
5. **UI (`kanban-module/src/ui/`):** Изолированный компонент `<KanbanBoard />` со строгим префиксом стилей `kb-*`, поддержкой темной/светлой темы, локализацией (i18n RU/EN) и реактивным SSE-транспортом.

### 2. Соглашения об изоляции (Isolation Conventions)
При модификации или интеграции модуля строго соблюдайте установленные префиксы:
- **Таблицы базы данных:** Префикс `kanban_*` (`kanban_boards`, `kanban_tasks`, `kanban_templates`, `kanban_chat_messages`).
- **REST & SSE маршруты:** Префикс `/api/kanban/*`.
- **Переменные окружения:** Префикс `KANBAN_*`.
- **CSS-классы UI:** Префикс `kb-*` и локальные CSS-переменные внутри контейнера `.kb-orchestrator-root`.
- **Ключи LocalStorage:** Префикс `kanban:*`.

## 🛡️ Правила безопасности и отказоустойчивости

1. **Защита от циклов в графе (Cycle Detection):**
   Перед созданием любой связи `A -> B` или запуском задач обязательно вызывается алгоритм детекции циклов на основе поиска в глубину (DFS с тремя цветами вершин: белые, серые, черные). Ни при каких обстоятельствах граф не должен содержать циклических зависимостей.
2. **Ограничение параллелизма (`maxParallel`):**
   Шедулер строго контролирует пул одновременно выполняемых задач. Задачи в статусе `ready` упорядочиваются по приоритету (`priority` DESC) и времени создания (`createdAt` ASC) и запускаются только при наличии свободных слотов.
3. **Каскадная блокировка (Cascade Failure Handling):**
   При переходе задачи в статус `failed` шедулер обязан автоматически рекурсивно обойти всех ее прямых и транзитивных потомков в статусе `backlog` или `ready` и перевести их в статус `blocked`, фиксируя причину сбоя в системном логе.
4. **Восстановление после сбоя сервера (`recoverPolicy`):**
   При старте приложения незавершенные задачи (`in_progress`) должны быть обработаны согласно политике: `fail` (перевод в `failed` с пометкой `interrupted`) либо `requeue` (возврат в `ready`).

## 🧪 Стандарты тестирования и верификации

- **Пирамида тестов:**
  - **Unit-тесты:** Полное покрытие доменного ядра (валидация DAG, обход слоев графа, парсер инструкций планировщика).
  - **Интеграционные тесты:** Тестирование шедулера с мок-исполнителями, каскадного автозапуска цепочек, вееров задач, адаптеров SQLite и REST API роутера.
  - **E2E тесты (Playwright):** Сквозная проверка взаимодействия пользователя с доской в реальном браузере: создание задач, Drag & Drop, запуск, просмотр логов и переключение между доской и графом.
- **Обязательная валидация перед коммитом:**
  Всегда запускайте полный набор тестов (`npm test`) и тайпчек (`npm run lint`), чтобы гарантировать 0 регрессий и отсутствие ошибок типизации.

## 📝 Стандарты оформления кода (Formatting & Comments Template)

При создании или редактировании кода руководствуйтесь следующим эталоном:

```typescript
/**
 * @file kanban-module/src/example/processor.ts
 * @description Сервисный процессор обработки очереди задач.
 *
 * Архитектурный контекст:
 * Входит в состав подсистемы диспетчеризации. Отвечает за проверку
 * готовности входных аргументов, валидацию контекста выполнения
 * и передачу управления конкретному зарегистрированному исполнителю.
 */

import { Task, ExecutionContext, ExecutionResult } from '../core/types';

/**
 * Опции конфигурации процессора очереди задач.
 */
export interface ProcessorOptions {
  /** Максимальное допустимое время ожидания блокировки ресурса в мс */
  readonly lockTimeoutMs: number;
  /** Включать ли подробный трассировочный лог каждого шага */
  readonly verboseLogging?: boolean;
}

/**
 * Класс TaskQueueProcessor инкапсулирует логику безопасного исполнения задачи.
 */
export class TaskQueueProcessor {
  private readonly options: ProcessorOptions;

  /**
   * Инициализирует процессор с переданными параметрами конфигурации.
   *
   * @param options Настройки процессора задач
   */
  constructor(options: ProcessorOptions) {
    this.options = { ...options };
  }

  /**
   * Выполняет предварительную валидацию задачи и запускает ее обработку.
   *
   * @param task Объект задачи, прошедший проверку зависимостей
   * @param ctx Контекст исполнения с шиной логов и токеном отмены
   * @returns Промис с результатом выполнения ExecutionResult
   * @throws {Error} Если задача находится в невалидном начальном статусе
   */
  public async process(task: Task, ctx: ExecutionContext): Promise<ExecutionResult> {
    // Шаг 1: Проверяем сигнал прерывания перед началом работы
    if (ctx.signal.aborted) {
      ctx.log('[Processor] Исполнение прервано до запуска (сигнал AbortSignal)');
      return { ok: false, error: 'Aborted before execution' };
    }

    // Шаг 2: Фиксация старта в логе задачи
    ctx.log(`[Processor] Старт задачи #${task.id} («${task.title}»)`);

    try {
      // Имитация или вызов реального шага
      return { ok: true, output: { processedAt: new Date().toISOString() } };
    } catch (err: unknown) {
      const errorMessage = err instanceof Error ? err.message : String(err);
      ctx.log(`[Processor] Критическая ошибка выполнения: ${errorMessage}`);
      return { ok: false, error: errorMessage };
    }
  }
}
```
