## 🧭 Обзор архитектурной парадигмы

Архитектура **CITY7Z7-Vibe-Drifter** базируется на принципах **чистой архитектуры (Clean Architecture)** и **гексагонального проектирования (Ports and Adapters)**. Доменная модель полностью отделена от транспортных протоколов (Express, SSE), пользовательского интерфейса (React) и конкретных драйверов баз данных.

## 1. Математическая модель графа (DAG)

Оркестратор моделирует взаимосвязи между задачами в виде **направленного ациклического графа (Directed Acyclic Graph — DAG)**: $G = (V, E)$, где:
- $V$ — множество задач (Tasks);
- $E$ — направленные ребра зависимостей: ребро $(u, v) \in E$ означает, что задача $v$ **зависит** от завершения задачи $u$ ($u \to v$). До тех пор, пока $u$ не перейдет в статус `done`, задача $v$ не может быть запущена шедулером.

### 1.1. Алгоритм детекции циклов (Three-Color DFS)
Для обеспечения ацикличности перед созданием любого ребра $u \to v$ или применением сгенерированного плана выполняется обход в глубину с трехцветной раскраской вершин (`validateGraphAcyclic` в `kanban-module/src/core/graph.ts`):
- `WHITE` (0) — вершина еще не посещена;
- `GRAY` (1) — вершина находится в текущем стеке рекурсии (активный путь);
- `BLACK` (2) — вершина и все ее потомки полностью исследованы.

Если в процессе обхода из текущей вершины ребро ведет в вершину цвета `GRAY`, обнаружен **обратный цикл (Back-Edge)**. Операция немедленно отклоняется с ошибкой `400 Bad Request` и точным указанием циклического контура (например: `Cycle detected: 1 -> 2 -> 3 -> 1`).

### 1.2. Вычисление ярусов топологической глубины (Topological Layers)
Для наглядного отображения карточек на графе слева направо используется функция `computeGraphLayers`:
1. Узлы без входящих зависимостей (`inDegree === 0`) помещаются на ярус $0$ (`depth = 0`).
2. Для каждого последующего узла глубина рассчитывается динамически:
   $$\text{depth}(v) = 1 + \max_{(u, v) \in E} \text{depth}(u)$$
3. Это гарантирует, что все ребра графа направлены строго слева направо, исключая визуальные перехлесты.

## 2. Конечный автомат состояний задачи (Task FSM)

Каждая задача обладает строго типизированным статусом жизненного цикла (`TaskStatus`):

```
                       ┌──────────────┐
                       │   backlog    │
                       └──────┬───────┘
                              │ Запуск (ручной или автоцепочка)
                              ▼
                       ┌──────────────┐
     ┌────────────────►│    ready     │◄────────────────┐
     │                 └──────┬───────┘                 │
     │                        │ Слот шедулера свободен  │ Retry (после сбоя)
     │                        ▼                         │
     │                 ┌──────────────┐                 │
     │                 │ in_progress  │                 │
     │                 └──┬───┬───┬───┘                 │
     │     Успех (авто)   │   │   │ Сбой / Таймаут      │
     │   ┌────────────────┘   │   └────────────────┐    │
     │   │                    │                    │    │
     │   │         Требует    ▼                    ▼    │
     │   │         ревью  ┌───────────┐      ┌──────────┴───┐
     │   │                │  review   │      │    failed    │
     │   │                └─┬───────┬─┘      └──────┬───────┘
     │   │     Подтверждено │       │ Отклонено     │
     │   │   ┌──────────────┘       └───────────┐   │ Каскадный сбой
     │   │   │                                  │   ▼
     │   ▼   ▼                                  │ ┌──────────────┐
     │ ┌───────┐                                └►│   blocked    │
     │ │ done  │                                  └──────────────┘
     │ └───┬───┘
     │     │ Разблокирует потомков
     └─────┘
```

### Таблица допустимых переходов (Transition Matrix)

| Исходный статус | Целевой статус | Триггер перехода | Описание |
|---|---|---|---|
| `backlog` | `ready` | Пользователь / Шедулер | Задача активирована и встает в очередь шедулера |
| `ready` | `in_progress` | Шедулер | Свободен слот `maxParallel`, зависимости в `done` |
| `in_progress` | `done` | Исполнитель (успех) | Завершено успешно (`requireReview === false`) |
| `in_progress` | `review` | Исполнитель / Флаг | Требуется ручной аппрув результата человеком |
| `in_progress` | `failed` | Исполнитель / Сбой | Ошибка, отмена или превышение таймаута |
| `review` | `done` | Аппрув (POST `/approve`) | Человек подтвердил качество артефакта |
| `review` | `failed` | Отклонение (POST `/reject`) | Человек отклонил результат |
| `failed` | `ready` | Повтор (POST `/retry`) | Сброс счетчика ошибок, каскадный возврат `blocked → ready` |
| `ready` / `backlog` | `blocked` | Каскадный движок | Предок упал в `failed` |
| Любой | `backlog` | Ручной Drag & Drop | Откат задачи в начальное состояние планирования |

## 3. Шедулер параллельного исполнения (Scheduler Engine)

Шедулер (`kanban-module/src/core/scheduler.ts`) функционирует как асинхронный диспетчер задач.

### 3.1. Алгоритм выборки задач (Dispatch Loop)
1. **Проверка паузы:** Если флаг `isPaused === true`, шедулер останавливает запуск новых задач.
2. **Подсчет занятых слотов:** Количество активных задач в статусе `in_progress` сравнивается с лимитом `board.settings.maxParallel` (по умолчанию 3, настраивается от 1 до 20).
3. **Поиск кандидатов:**
   - Выбираются все задачи со статусом `ready`.
   - Для каждой задачи проверяется предикат: **все задачи из `task.dependsOn` имеют статус `done`**.
   - Дополнительно проверяется: ни одна из зависимостей не находится в статусе `failed` или `blocked`.
4. **Приоритизация:**
   - Кандидаты сортируются по убыванию `priority` (задачи с высоким приоритетом запускаются первыми).
   - При равном приоритете побеждает более ранняя задача (`createdAt` ASC).
5. **Запуск воркера:** Свободные слоты заполняются отобранными задачами, статус переводится в `in_progress`.

### 3.2. Каскадный автозапуск цепочек (`autoChain`)
При успешном завершении задачи $T$ шедулер:
1. Фиксирует статус `done` в хранилище.
2. Находит всех прямых потомков $C$, у которых $T \in C.\text{dependsOn}$.
3. Если параметр доски `settings.autoChain === true` и задача $C$ находится в статусе `backlog`, она автоматически переводится в статус `ready`.
4. Немедленно инициируется цикл шедулера (`scheduler.tick()`).

### 3.3. Каскадная блокировка при сбое (Cascade Failure)
Если задача $T$ падает со статусом `failed`:
1. Шедулер рекурсивно находит всех транзитивных потомков в графе.
2. Задачи-потомки в статусах `backlog` или `ready` переводятся в статус `blocked`.
3. В системный журнал задач записывается причина: `[Cascade] Заблокирована из-за ошибки в предке #${T.id}`.

### 3.4. Умный повтор (Smart Retry)
При вызове `POST /tasks/:id/retry` для упавшей задачи:
1. Статус целевой задачи сбрасывается в `ready`.
2. Очищается поле ошибки `error = undefined`.
3. Все потомки, переведенные ранее в `blocked`, возвращаются в статус `ready` (или `backlog`), восстанавливая целостность цепочки.

## 4. Реактивная шина данных (SSE Transport)

Связь между бэкендом и фронтендом осуществляется по протоколу **Server-Sent Events (SSE)** через эндпоинт `GET /api/kanban/events`:
- **Низкие накладные расходы:** Одно постоянное HTTP-соединение вместо тяжелого полинга.
- **Heartbeat (Keep-Alive):** Каждые 15 секунд сервер отправляет служебный комментарий `: ping\n\n`, предотвращая закрытие соединения обратными прокси-серверами (Nginx, Cloudflare).
- **События в реальном времени:**
  - `task:created` — новая задача на доске;
  - `task:updated` — смена статуса, инкремент попыток, обновление полей;
  - `task:log` — потоковая строка лога исполнения (мгновенный вывод в терминал UI);
  - `task:progress` — процент готовности задачи (0–100%);
  - `board:updated` — изменение параметров параллелизма `maxParallel` или паузы.

## 5. Слой абстракции хранилища (Storage Layer)

Контракт `StorageAdapter` (`kanban-module/src/storage/types.ts`) определяет набор методов для персистентности:
- `listBoards()`, `getBoard(id)`, `createBoard(b)`, `updateBoard(id, patch)`, `deleteBoard(id)`
- `listTasks(boardId)`, `getTask(id)`, `createTask(t)`, `updateTask(id, patch)`, `deleteTask(id)`
- `listLinks(boardId)`, `addLink(from, to)`, `removeLink(from, to)`
- `listTemplates()`, `createTemplate(t)`, `getChatMessages(boardId)`, `addChatMessage(msg)`

### Реализации в поставке:
1. **`SQLiteStorageAdapter`:** Продакшн-адаптер на `better-sqlite3`. Автоматически создает таблицы с префиксом `kanban_*`, активирует `PRAGMA journal_mode = WAL` для параллельного чтения/записи и `PRAGMA foreign_keys = ON` для ссылочной целостности.
2. **`MemoryStorageAdapter`:** Легковесный адаптер в оперативной памяти (RAM) на базе структур `Map`. Идеален для быстрых изолированных юнит-тестов без дискового ввода-вывода.

## 6. Исполнители задач (Pluggable TaskExecutors)

Каждый воркер реализует интерфейс `TaskExecutor`:
```typescript
export interface TaskExecutor {
  readonly id: string;
  run(task: Task, ctx: ExecutionContext): Promise<ExecutionResult>;
}
```

Контекст `ExecutionContext` предоставляет:
- `signal: AbortSignal` — для корректного прерывания длительных операций при отмене задачи пользователем;
- `log: (msg: string) => void` — для отправки строк в журнал задачи с немедленной трансляцией по SSE;
- `deps: Record<string, { output: unknown }>` — результаты выполнения всех задач, от которых зависела данная;
- `progress: (pct: number) => void` — трансляция прогресса в процентах.
